# Phase 1 — Zernio client (Option B foundation)

**Objective:** a server-side Zernio client inside MGOS that is safe to call, honest about
failure, and never blocks boot. This is the only component that talks to Zernio. Every
later phase depends on it.

---

## 1.1 Contract extracted from nabra-smma (facts, not guesses)

| Item | Value |
|---|---|
| Base URL | `ZERNIO_BASE_URL` default `https://zernio.com/api/v1` |
| Auth | `Authorization: Bearer ${ZERNIO_API_KEY}` |
| Webhook secret | `ZERNIO_WEBHOOK_SECRET`, 32+ random hex bytes, **generated by us** |
| Client request budget | `ZERNIO_RPM` default 500 |
| Zernio-side limit | 600/min for 3–2,000 connected accounts |
| Webhook receiver | `POST /api/webhooks/zernio`, signed |
| Mode switch | `NABRA_SOCIAL_PROVIDER` = `native` \| `zernio` |

**Anti-pattern inherited from nabra-smma that MGOS must NOT copy:** in nabra, `zernio` mode
is *exclusive* and the server **refuses to boot** without the key and secret. In MGOS a
missing Zernio credential must degrade the feature, never stop the CRM. A CRM that will not
start because an ads integration is misconfigured is a worse outage than a blank ads page.

## 1.3 Transport rules

| Rule | Why |
|---|---|
| Timeout per request (connect 5 s, read 20 s) | A hung ad platform must not hang a request thread |
| Retry only on 429 / 5xx / network, max 3, exponential **backoff** with jitter | Retrying a 400 duplicates nothing and hides bugs |
| Honour `Retry-After` and rate-limit headers | Cheapest correct behaviour |
| **Circuit breaker** per platform endpoint | A platform **outage** must fail fast, not queue 10k requests |
| Every mutating call carries an **idempotency key** | Prevents **duplicate post** / duplicate campaign on retry |
| No credential ever logged | Same rule as the rest of the estate |

## 1.4 Error taxonomy

Every failure maps to exactly one class, because the UI copy differs for each:

| Class | Trigger | User-facing meaning |
|---|---|---|
| `AUTH_INVALID` | 401/403 | Key rejected — ops problem, not user |
| `TOKEN_REVOKED` | provider says connection dead | **account disconnected** — user must reconnect |
| `TOKEN_EXPIRED` | refresh failed | reconnect required |
| `RATE_LIMITED` | 429 | try again in N seconds |
| `QUOTA_EXHAUSTED` | provider quota | daily limit reached |
| `PLATFORM_OUTAGE` | 5xx / circuit open | provider is down, not us |
| `POLICY_REJECTED` | ad **rejection** / **disapproval** | creative violates policy; see 1.7 |
| `VALIDATION` | our bug or bad input | report it |
| `UNKNOWN` | anything else | surface the trace id |

A `partial success` is its own state: some platforms succeeded, some failed. Never collapse
it into success or failure — the user must see which **social account** or **ad account**
landed and which did not.

## 1.5 Webhook receiver (the real cost of Option B)

Option B means MGOS rebuilds what nabra-smma already had. Required:

1. **Signature** verification over the raw body using `ZERNIO_WEBHOOK_SECRET` (HMAC-SHA256).
2. **Replay protection**: timestamp tolerance window + nonce store.
3. **Idempotency**: event id dedupe table; a replayed event is a no-op.
4. **Body limits** and content-type allowlist.
5. Return 2xx fast, then process async through a **queue** + **worker**, with a
   **dead letter queue** for poison events.
6. **Secret rotation** procedure: accept both old and new secret during a rotation window.

If Mohammed declines a public HTTPS endpoint for the receiver, the fallback is scheduled
**polling** via **cron** `sync job` instead. That is slower but avoids inbound exposure.
This is gate G-3 in Phase 0.

## 1.6 Capability map

Mirror nabra-smma's `ZERNIO_SUPPORT` idea: not every platform supports every capability.
A single source of truth prevents the UI offering a button the provider will reject.

```ts
type Capability =
  | 'connect' | 'launch_campaign' | 'pause_campaign' | 'update_budget'
  | 'read_insights' | 'read_audience_estimate' | 'publish_content' | 'schedule_content';

// platform -> capability -> supported
```

Anything unsupported is disabled in the UI **and** refused server-side. Two checks, because
a disabled button is not a permission.

## 1.7 Ad policy handling

Providers reject ads. MGOS must model this explicitly:

| Concept | Handling |
|---|---|
| ad policy, review status | mirror provider status per ad |
| rejection, disapproval | store reason verbatim, never paraphrase |
| appeal | link out; MGOS does not automate appeals |
| restricted category | surface before launch: **housing**, **employment**, **credit**, **political ads** |
| special ad category | required for real-estate in several markets — must be selectable |
| age gate | enforce provider minimums, refuse silently-invalid targeting |
| consent, GDPR | no PII forwarded to a platform without recorded basis |
| disclosure, sponsored label | required on organic posts in several jurisdictions |
| brand safety, trademark | blocklist check before publish |
| platform rate limit, terms of service | surfaced in the ops runbook |

Real-estate is a **housing** special category on Meta in many markets. That single fact
changes targeting options and cannot be added later — it belongs in the launch form.
